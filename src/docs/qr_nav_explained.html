From paper QR card to moving robot

A walkthrough of the qr_nav ROS 2 pipeline running on a Husarion ROSbot 3 PRO. We trace one printed QR card through the OAK-D camera, the OpenCV detector, the finite-state interpreter, and out to the motor controller — the same path every command takes, every time.

01System overview

qr_nav is a perception-to-action loop split across three ROS 2 nodes. Each node has one job, and they communicate exclusively over named topics — no node calls another directly. This is what lets us boot the detector by itself for testing, swap in a fake /cmd_vel destination during dry-runs, or replay a logged session.

hardware perception policy / FSM actuation observability (passive tap)
TopicTypePublisher → SubscribersCarries
/oak/rgb/image_raw sensor_msgs/Image OAK driver → qr_detector Raw 1080p RGB frames at ~10 Hz (Pi 5 CPU-bound).
/qr_command std_msgs/String qr_detector → command_interpreter, qr_logger One of 7 validated command strings, debounced 1.0 s.
/qr_detections std_msgs/String (JSON) qr_detector → qr_logger Every decode this tick, valid or not, with bbox area.
/cmd_vel geometry_msgs/TwistStamped command_interpreter → motor controller, qr_logger Linear x and angular z, published at 20 Hz.
/nav_state std_msgs/String command_interpreter → qr_logger Current FSM state name.

02Step 0 — Generating QR cards (offline, on the laptop)

Before the robot ever sees a card, the cards have to exist. They're generated by src/utils/generate_qr_cards.py, which parses the detector source itself with Python's ast module to extract the VALID_COMMANDS set. The printed cards are therefore guaranteed to match the strings the detector actually accepts — no chance of "the card said TURNLEFT but the code checks TURN_LEFT".

python  src/utils/generate_qr_cards.py
def load_valid_commands(source_path: Path) -> list[str]:
    """Extract the VALID_COMMANDS set literal from the detector source."""
    tree = ast.parse(source_path.read_text())
    for node in tree.body:
        if not isinstance(node, ast.Assign): continue
        targets = [t.id for t in node.targets if isinstance(t, ast.Name)]
        if "VALID_COMMANDS" not in targets: continue
        # node.value is an ast.Set whose elts are ast.Constant strings
        return sorted(elt.value for elt in node.value.elts)

For each command it renders an A4 page at 150 DPI containing a ~12 cm QR with error-correction level H (~30% damage tolerance) and a large human-readable label, then concatenates them into qr_cards/all_commands.pdf. The print instruction is explicit: 100% scale, no "fit to page", so the QR's apparent size at a given distance is predictable — which matters because the detector uses bounding-box area both as a quality filter and as a tiebreak between simultaneously-visible cards.

03Step 1 — Camera capture

The Husarion bring-up brings up the OAK-D Pro under the /oak/... namespace (not the depthai-ros default /camera/camera/...), publishing the colour image as sensor_msgs/Image at roughly 10 Hz on a Pi 5. Two details matter for the subscriber:

  • The topic name must literally be /oak/rgb/image_raw. We discovered this with ros2 topic list | grep oak on the actual robot — the depthai-ros documentation defaults are not what Husarion ships.
  • The QoS reliability must match the publisher. Husarion's OAK-D publishes RELIABLE / VOLATILE; a BEST_EFFORT subscriber against a RELIABLE publisher silently receives zero callbacks. ROS 2 rejects the QoS contract without raising an error.
Failure mode: If the QoS is wrong, the detector node starts cleanly, /qr_command never fires, and there are no logs to tell you why. The startup banner therefore prints the resolved QoS string so it's verifiable at a glance.

if qos_reliability_str == 'best_effort':
    reliability = ReliabilityPolicy.BEST_EFFORT

    reliability = ReliabilityPolicy.RELIABLE
else:
    self.get_logger().warn(...)
    reliability = ReliabilityPolicy.RELIABLE

camera_qos = QoSProfile(
    depth=10,
    reliability=reliability,
    durability=DurabilityPolicy.VOLATILE,
)

self.image_sub = self.create_subscription(

04Step 2 — Detection & decode

Every incoming frame triggers image_callback. Two cheap guards come first to keep the Pi 5 from being saturated:

  1. Rate limit: we only process at most detection_rate_hz (15 Hz cap) — frames arriving faster than that are dropped silently. The camera itself runs at ~10 Hz, so in practice we process every frame, but the cap protects us if the driver bursts.
  2. Conversion: cv_bridge turns the ROS Image into an OpenCV BGR ndarray.

2a. Two-stage decode pipeline

OpenCV's cv2.QRCodeDetector is fast but brittle on uneven lighting. The detector therefore runs two passes:

Pass 1 — Standard
Grayscale + CLAHE
Contrast-Limited Adaptive Histogram Equalisation (clipLimit=2.0, 8×8 tiles) flattens harsh shadows and lifts mid-tones — the single biggest win for cards held at oblique angles.
Pass 2 — Fallback (only if pass 1 finds nothing)
Adaptive threshold
cv2.adaptiveThreshold(..., GAUSSIAN_C, blockSize=11, C=2) binarises the CLAHE output. Recovers crumpled, faded, or partially-blown-out codes that pass 1 misses.
python  qr_detector_node.py · two-stage decode
gray = cv2.cvtColor(cv_image, cv2.COLOR_BGR2GRAY)
clahe = cv2.createCLAHE(clipLimit=2.0, tileGridSize=(8, 8))
enhanced = clahe.apply(gray)

detections = self._detect_qr_codes(enhanced)

if not detections:
    thresh = cv2.adaptiveThreshold(
        enhanced, 255,
        cv2.ADAPTIVE_THRESH_GAUSSIAN_C, cv2.THRESH_BINARY,
        blockSize=11, C=2,
    )
    detections = self._detect_qr_codes(thresh)

2b. _detect_qr_codes — multi-QR aware

We use detectAndDecodeMulti rather than the single-target detectAndDecode, because we want to handle the case where two cards are in frame at once. For each decoded string we compute the bounding-box area from the four corner points returned by OpenCV.

OpenCV 4.6 quirk: cv2.contourArea on the Jazzy default OpenCV requires the points to be CV_32F or CV_32S. np.float64 (the default for .astype(float)) raises (-215:Assertion failed) depth == CV_32F || CV_32S. The cast to np.float32 is wrapped in try/except so a single malformed detection becomes a warning, not a crash that strands the robot mid-run.
python  qr_detector_node.py · _detect_qr_codes
retval, decoded_info, points, _ = self.qr_detector.detectAndDecodeMulti(image)
if not retval or decoded_info is None or points is None:
    return []

detections = []
for i, content in enumerate(decoded_info):
    if not content: continue
    try:
        bbox_points = np.asarray(points[i], dtype=np.float32)
        bbox_area   = cv2.contourArea(bbox_points)
    except Exception as e:
        self.get_logger().warn(f"Skipping detection ...")
        continue
    detections.append((content.strip(), bbox_area))
return detections

05Step 3 — Validate, debounce, publish

A successful decode is necessary but not sufficient. Three filters run before anything is sent to the FSM:

FilterWhat it rejectsWhy
Allow-list against VALID_COMMANDS Any string that isn't one of the 7 known commands. QR codes in the wild (posters, packaging) decode happily but mean nothing to us.
Min bbox area (min_bbox_area=500 px) Cards too far away or too oblique to decode reliably. Below this size the decode is a coin-flip; we'd rather miss it than misfire.
Largest-bbox tiebreak All-but-one of multiple simultaneously-valid detections. Spatial proxy for "what is the operator pointing at?" — closer card wins.
Per-command cooldown (1.0 s) The same command repeating within 1 s. At 15 Hz we'd otherwise re-fire the same command 15× per second, slamming the FSM.

All raw decodes (valid or not) are still published on /qr_detections for the logger, so we can post-mortem "why didn't card X fire?" later. Only the survivor of the four filters lands on /qr_command.

python  qr_detector_node.py · final filters
for content, bbox_area in detections:
    all_detections.append({'timestamp': ts, 'content': content, 'bbox_area': bbox_area})
    if content in VALID_COMMANDS and bbox_area >= self.min_bbox_area:
        valid_detections.append((content, bbox_area))

self.detections_pub.publish(String(data=json.dumps(all_detections)))

if not valid_detections: return

best_command, best_area = max(valid_detections, key=lambda x: x[1])

last_time = self.last_command_time.get(best_command, 0.0)
if now - last_time < self.cooldown_sec: return

self.command_pub.publish(String(data=best_command))
self.last_command_time[best_command] = now

06Step 4 — FSM interpreter

command_interpreter_node turns command strings into motion. It runs two things in parallel: a callback on /qr_command that changes state, and a 20 Hz timer (control_loop) that publishes velocity based on whatever state we're currently in. Decoupling these is what lets a TURNING state run for a fixed wall-clock duration without blocking command reception.

The five states

StateVelocity outputAcceptsExit condition
IDLE 0.0, 0.0 Only GO GO command → DRIVING
DRIVING cruise_speed, 0.0 Any valid command Command, or recovery_timeout elapsed
TURNING 0.0, ±turn_speed Nothing — commands ignored turn_duration elapsed → DRIVING
STOPPED 0.0, 0.0 Only GO GO command → DRIVING
RECOVERING min_speed, 0.0 (creep) Any valid command Any command

State transition diagram

boot state active driving blocking turn (commands ignored) operator halt (GO-only) vision-loss safety creep

Why IDLE exists

The FSM boots into IDLE, not DRIVING. This is deliberate: launching the stack never moves the robot on its own. A human must show a GO card to deliberately arm the bot. Once armed, IDLE is unreachable — the FSM only ever cycles between DRIVING, TURNING, STOPPED, and RECOVERING.

The control loop (20 Hz)

The state callback changes state. The 20 Hz control timer enacts it. This separation is what lets TURNING work with no extra threads: when the timer fires and the state is TURNING, it checks elapsed time, and either keeps emitting (0, ±turn_speed) or transitions back to DRIVING.

python  command_interpreter_node.py · control_loop
def control_loop(self):
    now = time.time()

    if self.state == State.IDLE:
        self._publish_velocity(0.0, 0.0); return

    if self.state == State.DRIVING:
        self._publish_velocity(self.cruise_speed, 0.0)
        if now - self.last_command_time >= self.recovery_timeout:
            self._transition_to(State.RECOVERING)

    elif self.state == State.TURNING:
        elapsed = now - self.turn_start_time
        if elapsed >= self.turn_duration:
            self._transition_to(State.DRIVING)
            self._publish_velocity(self.cruise_speed, 0.0)
        else:
            self._publish_velocity(0.0, self.turn_angular_z)

    elif self.state == State.STOPPED:
        self._publish_velocity(0.0, 0.0)

    elif self.state == State.RECOVERING:
        self._publish_velocity(self.min_speed, 0.0)

Turn duration is open-loop

We deliberately do not consume odometry or IMU here. TURNING runs for a fixed turn_90_duration seconds at a fixed turn_speed rad/s. The duration is derived from the geometry: 

turn_90_duration  = π/2 / turn_speed   ≈ 1.5708 / 0.4 ≈ 3.93 s  → rounded to 4.0
turn_180_duration = π   / turn_speed   ≈ 3.1416 / 0.4 ≈ 7.85 s  → rounded to 8.0

The trade-off is that turn accuracy drifts with battery sag and floor friction. For this assignment that's acceptable — turns are calibrated with wheels in the air (Stage 3 of the deploy guide), and the assignment rubric doesn't require closed-loop heading. Moving to closed loop would be a roughly <50-line change: subscribe to /odom, integrate yaw, and exit TURNING when |Δyaw| ≥ target.

07Step 5 — Motor command

The interpreter publishes to /cmd_vel as geometry_msgs/TwistStamped — not plain Twist. ROS 2 Jazzy's Husarion bring-up uses the stamped variant, and a type mismatch produces no error: the topic just silently fails to match and the base controller never sees our messages. This is the single most common foot-gun on the platform.

python  command_interpreter_node.py · _publish_velocity
def _publish_velocity(self, linear_x: float, angular_z: float):
    msg = TwistStamped()
    msg.header.stamp    = self.get_clock().now().to_msg()
    msg.header.frame_id = self.cmd_vel_frame_id   # 'base_link' (REP-105)
    msg.twist.linear.x  = linear_x
    msg.twist.angular.z = angular_z
    self.cmd_vel_pub.publish(msg)

Shutdown safety: on KeyboardInterrupt the node publishes one final empty TwistStamped before destroying itself, so a Ctrl-C reliably stops the wheels rather than leaving the last commanded velocity to coast.

08Step 6 — Data logger

data_logger_node is a passive observer. It subscribes to every interesting topic and writes a row to a CSV at 5 Hz, plus prints a per-command and per-state-time summary on shutdown. Two things make it useful for the report:

  • It records both /qr_command (what fired) and /qr_detections (every raw decode this tick), so we can compute detection accuracy ("we saw the card but didn't fire") separately from execution accuracy ("we fired but the wrong thing happened").
  • It accumulates per-state wall time on every /nav_state change, giving the "% of run spent in RECOVERING" number that's the most honest single measure of run health.
csv  qr_log_*.csv columns
timestamp, elapsed_s, qr_command, all_detections,
nav_state, cmd_linear_x, cmd_angular_z, detection_event
Operational note: logs land in /tmp/qr_nav_logs/, which wipes on reboot. The deploy guide tells operators to scp them off before powering down.

09Launch & configuration

One launch file brings up all three nodes with a single shared YAML config. All tunables — speeds, turn durations, QoS, log directory — live in config/qr_params.yaml, so re-tuning never requires a recompile.

bash  Launch the full stack
# Motors live
ros2 launch qr_nav qr_nav.launch.py

# Motors diverted to a dummy topic — safe dry-run on the floor
ros2 launch qr_nav qr_nav.launch.py cmd_vel_topic:=/cmd_vel_dummy

The cmd_vel_topic launch argument matters: ros2 launch doesn't accept arbitrary --ros-args --remap flags, so the remap has to be wired through a declared launch argument that flows into both the interpreter (publisher) and the logger (subscriber). This is the mechanism behind Stage 2 of the deploy guide — a full launch where the wheels can't possibly turn.

yaml  config/qr_params.yaml (key entries)
qr_detector:
  ros__parameters:
    rgb_image_topic: "/oak/rgb/image_raw"
    detection_rate_hz: 15.0
    min_bbox_area: 500
    image_qos_reliability: "reliable"

command_interpreter:
  ros__parameters:
    cruise_speed:       0.1   # m/s 
    turn_speed:         0.4    # rad/s
    turn_90_duration:   4.0    # s     (= π/2 / turn_speed, rounded up)
    turn_180_duration:  8.0    # s     (= 2 × turn_90_duration)
    control_rate_hz:    20.0
    recovery_timeout:   3.0    # enter RECOVERING after no command

qr_logger:
  ros__parameters:
    log_directory: "/tmp/qr_nav_logs"
    log_rate_hz:   5.0

10End-to-end trace — one card, one motion

Putting it all together. Here's what happens, in order, from the moment a TURN_LEFT card enters the camera frame to the moment the wheels stop turning. Each step is real code, not pseudo-code.

t = 0.000 s

1 · OAK-D publishes a frame

A 1920×1080 BGR8 sensor_msgs/Image arrives on /oak/rgb/image_raw. The detector's RELIABLE subscriber accepts it.

t = 0.001 s

2 · Rate gate

image_callback checks the rate limiter (15 Hz); the previous frame was ≥66 ms ago, so we proceed.

t = 0.002 s

3 · Convert & preprocess

cv_bridge hands us a BGR ndarray. We grayscale and apply CLAHE — the QR is now high-contrast even though the room lighting is uneven.

t = 0.012 s

4 · OpenCV decodes

detectAndDecodeMulti returns retval=True and one decoded string: "TURN_LEFT". Bounding-box area: ~38 000 px² (well above the 500 px floor).

t = 0.013 s

5 · Validate & publish

"TURN_LEFT" ∈ VALID_COMMANDS ✓. No other valid detections, so the largest-bbox tiebreak is trivial. Last TURN_LEFT fired > 1.0 s ago, cooldown clears. String("TURN_LEFT") is published on /qr_command.

t = 0.014 s

6 · Interpreter receives

command_callback fires. We're in DRIVING, which accepts everything. _execute_command("TURN_LEFT") sets turn_angular_z = +0.4, turn_duration = 4.0 s, transitions to TURNING, and publishes "TURNING" on /nav_state.

t = 0.014 – 4.014 s

7 · Control loop turns

Every 50 ms the timer wakes up, sees state TURNING, checks elapsed < 4.0 s, publishes TwistStamped(linear.x=0, angular.z=+0.4) on /cmd_vel. The base controller spins the wheels left. ~80 messages are sent over the 4-second turn.

t = 4.014 s

8 · Turn complete

Elapsed ≥ 4.0 s. Transition to DRIVING, publish "DRIVING" on /nav_state, immediately emit TwistStamped(0.1, 0). Wheels resume forward.

throughout

9 · Logger captures everything

The data logger writes 5 rows/second containing the latest command, state, and twist values. On shutdown it prints "TURN_LEFT: 1, time in TURNING: 4.0 s (8.7%)".

11Why these specific choices

Most of the design decisions in qr_nav come from a specific failure observed during bring-up. The system is small enough that every defensive line of code can be traced to a real bug.

DecisionFailure it prevents
QoS reliability is a parameter, banner prints which one was applied Subscriber silently receives zero callbacks if QoS doesn't match the publisher.
TwistStamped on /cmd_vel with frame_id="base_link" Plain Twist never reaches the Husarion base controller on Jazzy.
cv2.contourArea(np.float32(points)) wrapped in try/except OpenCV 4.6 rejects float64 contours; one bad detection would otherwise crash the node and strand the robot.
FSM boots into IDLE, requires arming card Stack launching at boot accidentally drives the robot off the bench.
Per-command 1.0 s cooldown 15 Hz detection × 1 card in frame = 15 redundant FSM transitions per second.
Largest-bbox tiebreak when multiple cards decode Random tiebreak would mean two cards in frame produces unpredictable behaviour.
STOPPED only releases on GO Operator wants a hard, deliberate halt; accidental drive-by of any other card shouldn't restart motion.
RECOVERING creeps at min_speed, doesn't full-stop Brief vision dropout shouldn't stall a delivery; full stop requires explicit STOP.
Detector + interpreter + logger are separate nodes Lets us run Stage 1 (detector only, robot stationary) and Stage 2 (full launch, motors diverted) without code changes.
Cards generated by AST-parsing VALID_COMMANDS from the detector Hand-edited cards drift from the strings the code accepts. Single source of truth eliminates the drift entirely.
The mental model: a QR card is just a serialised command with optical error correction. Everything in this pipeline is either decoding it, validating that it's safe to act on, or executing it as a velocity. There is no other state in the system.
